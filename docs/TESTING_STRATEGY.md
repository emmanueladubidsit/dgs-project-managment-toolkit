# Testing strategy

Testing is part of every increment. Current status: **all suites passing**.

| Suite | Tool | Command | Count |
| --- | --- | --- | --- |
| Backend API, rules and calculations | pytest + FastAPI TestClient | `cd backend && uv run pytest` | 99 |
| Frontend components and helpers | Vitest + Testing Library (jsdom) | `cd frontend && npm test` | 21 |
| End-to-end user journeys | Playwright (Chromium) | `cd frontend && npx playwright test` | 9 |

## Backend (`backend/tests`)

- Runs against the separate `dgs_workspace_test` database; the suite **refuses to start** if the
  database name does not contain `test`. Real Alembic migrations are applied, so migrations are
  tested too; data is truncated after every test.
- Covers: project CRUD, validation, search, archive/restore, name-confirmed deletion; stage
  seeding; milestone lifecycle and warnings; workstream deletion keeping tasks; task defaults,
  history, no-op updates, status/progress independence, completion and reopening; subtasks never
  auto-completing parents; parent and dependency cycle rejection; cross-project reference
  rejection; blocked detection; filters and sorting; comments; bulk update; archive and confirmed
  deletion; Kanban reordering; weighted progress rules; day/week/month planning, capacity and
  carry-forward; plan checks; work logs; reports containing only real data; dashboard; admin info
  without secrets; consistent error bodies.

Library modules (`test_knowledge.py`, `test_methodologies.py`, `test_documents.py`,
`test_voice.py`): template validation, versioning and restore, origin/reuse rules, evidence and
supersede relations, work-log promotion; methodology structure, publishing, versioning, whole and
partial adoption without duplicate tasks, deliverable tracking, duplicate, create-from-project,
delete rules and idempotent seeding; **document security** — root validation (relative, missing,
`/`, home, `/etc`, file), scans excluding secrets, dependencies, hidden files and symlinks,
traversal and symlink-escape refusal, read-only guarantees (files survive record and folder
removal), missing-file detection, link scheme validation; voice text cleaning, classification and
duplicate similarity, honest AI-output refusal, suggestion review (duplicate refusal, edits,
approval, rejection, deferral, no re-suggestion), unavailable providers saving nothing, and audio
retention (deleted by default, kept on request, deletable).

AI and exports (`test_ai.py`, `test_exports.py`): run against a **fake OpenAI-compatible server**
(real request/response shape) — disabled by default, settings validation, connection test and
model listing, grounded prompts containing project data and the no-invention rules, sources
returned, writing outputs, AI suggestions with priority normalisation and duplicate flags,
subtask breakdown creating child tasks on approval, unsaved project-brief drafts, research drafts
marked as AI suggestions, malformed answers and HTTP errors explained, usage log without content,
and the copy-and-paste round trip. Exports: Markdown parsing, Word/PDF/PowerPoint rendering
(including characters outside the PDF font), every project/report/knowledge endpoint and MIME type.

Claude Code sync (`test_claude.py`): folder validation and one-folder-per-project, git history
import against a real temporary repository (no author names stored, no suggestions from history),
commit-to-task matching and approval with history, the folder left untouched, hook token checks,
Stop summaries with secret redaction and name masking, subagent and unknown-folder handling,
TaskCompleted matching and fallback, MCP context/report/update endpoints, and masked exports.
The MCP server was also exercised over stdio with an MCP client (as Claude Code launches it), and
the generated hook command was run with a Stop payload.

**Local Whisper** was verified manually with real speech generated by macOS `say`: transcribed
word for word, audio deleted after transcription, no temporary files left.

## Frontend (`frontend/src/**/*.test.tsx`)

British date formatting and local-date parsing; status/priority badges and their accessible
names; progress bars (ARIA, clamping, explanation); error state with retry; task table empty
state, overdue and dependency flags, and a bulk update that sends the right API request; Kanban
column placement and ordering; filter bar behaviour; activity-history wording; verification labels
and the AI-suggestion warning; deliverable classifications; recorder behaviour when recording is
unsupported or no provider exists.

## End-to-end (`frontend/e2e/journey.spec.ts`)

Runs against the running app (`make api` and `make web-prod`). Data is uniquely named and deleted
afterwards. The journey: create a project → workstream → milestone → task (linked, estimated, with
acceptance criteria) → subtask → schedule for today → move to In Progress (verified on the board
and in the daily planner) → record a progress update and a research note → generate a weekly report
containing that data → open a fresh browser session and confirm everything persisted. A second
test covers failure handling (unknown project, type-the-name delete confirmation). The journey now
includes step 10 (create a reusable knowledge item linked to the project). `library.spec.ts`
adopts a starter methodology and tracks a deliverable, turns pasted notes into a reviewed task
without duplicates, and adds a document link found through global search. `assistant.spec.ts`
asks a grounded question and turns notes into an approved task through copy-and-paste mode, and
downloads a stakeholder status deck. `codebase.spec.ts` connects a temporary git repository,
syncs a commit that mentions a task and applies the suggested task update.

**Restart persistence** was additionally verified manually: a record created via the API survived
stopping the API and restarting the PostgreSQL container.

## Not yet covered (known gaps)

- Browser recording itself (MediaRecorder) is not automated; upload and transcription are.
- Drag and drop is exercised by unit logic and manually, not by Playwright.
- No automated responsive-layout or accessibility audit (axe) yet — planned for Phase 10.
- No load or performance testing (single-user local app).
